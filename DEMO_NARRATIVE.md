## Part 1 — The Problem (why this exists)

### 1.1 What bank reconciliation actually is

Every business has two views of its money:

1. The **bank statement** — what the bank says happened. Raw, noisy, abbreviated.
   Example: `SQ * BROOKLYN BK ROASTERS 0099 04/15`
2. The **books** — what the accountant recorded. Structured, human-labelled.
   Example: Invoice INV-044, Vendor: Brooklyn Book Roasters, £312.00, due April 15.

**Reconciliation** is the process of confirming that every line on the bank statement has
a matching record in the books. The moment you can match all of them — with the right
vendor, right amount, right date — you know your books are clean, your cash position is
real, and you're audit-ready.

The hard part: **bank statements are generated by payment processors, not accountants.**
They carry transaction IDs, location suffixes, abbreviated merchant names, and noise that
was never designed to be human-readable. The names of the same vendor can look completely
different depending on which card terminal they used last Tuesday.

### 1.2 Why this is still a painful manual job

Even in 2025, most small-to-mid businesses reconcile manually in spreadsheets, or delegate
it entirely to their accountant (expensive), or use a basic accounting platform that does
"rule-based" matching — which means the person has to teach it every single edge case.

The core limitation everywhere is this: **existing tools match on exact rules**. They look
for an exact amount, or an exact date. If a vendor name is slightly different — or a payment
cleared two days late because of a bank delay — the rule breaks, and it's back to manual.

The question that started this project: **can we build a system that reasons about a
mismatch the same way a good accountant would?** Not just "does this string equal that
string" but "given everything we know — the vendor's payment history, the amount proximity,
the description similarity — is this the same transaction?"

## Part 2 — What we built (the current system, in full detail)

### 2.1 Architecture overview

The system has three layers:

```
[ Bank statement (CSV / PDF) ]
          ↓
[ Extraction layer ]  ← Gemini Vision parses PDFs
          ↓
[ Matching engine ] ← DETERMINISTIC Python: normalizer + fuzzy + embeddings + PuLP
          ↓
[ Human-in-the-loop UI ]  ← React app where a human approves/rejects suggestions
          ↓
[ Audit log ]  ← every decision recorded with its full reasoning chain
```

**The matching engine is not AI.** This is the most important design decision in the system.
AI is used for:
- **PDF extraction** (reading a scanned bank statement — Gemini Vision)
- **The chat assistant** (answering questions in plain English — Groq llama-3.3-70b)
- **Match narration** (explaining *why* a match was suggested — LLM traces the reasoning path)
- **Last-resort matching** (a single batched LLM call for whatever the deterministic engine
  couldn't match — and all its results are capped at "speculative", always needing human approval)

The core matching — the thing that processes 500 transactions and finds 80% of the answers
in under a second — is **plain, deterministic Python maths**. This is a deliberate choice.

> **Why no AI for matching?**
> 1. **Auditability.** When a match is wrong in a set of books, you need to explain *exactly*
>    why that suggestion was made. "A language model thought so" is not an audit trail.
>    "Jaro-Winkler similarity 0.94 on normalized vendor names + amounts within £0.02 + date
>    within 3 days = score 0.97" is.
> 2. **Determinism.** Running the same statement twice must give the same result. LLMs are
>    stochastic — they can't guarantee this.
> 3. **Speed.** The deterministic engine runs a 500-line statement in under one second on
>    a laptop. A full LLM pass on every pair would be prohibitively slow and expensive.
> 4. **Trust gates.** LLM suggestions always need human approval; deterministic high-confidence
>    matches can be pre-approved. You can't have two tiers of trust if everything comes from
>    the same source.

### 2.2 The matching engine — the 6-level cascade

Every bank line passes through these levels in order. The first level that fires wins;
subsequent levels are skipped.

---

#### Level 1 — Exact Match (confidence: 1.0)

**The rule:** `date == date AND amount == amount (to 2 decimal places)`

If a bank line on 15-Apr for £312.00 matches a ledger entry on 15-Apr for £312.00, that
is an exact match. Confidence 1.0. No human review required — this is the only level that
can auto-approve.

If multiple ledger entries have the same date and amount, we break the tie by running a
description similarity check on all of them and picking the closest one.

**In numbers:** roughly 40-60% of transactions in typical real-world data are caught here.

---

#### Level 2 — Amount + Date Fuzzy Match (confidence: 0.5–0.9)

**The rule:** `|amount_diff| ≤ tolerance AND date within window`

Real-world problems this solves:
- A payment clears 2 days after the ledger entry (payment terms, bank processing delay).
- A foreign-currency transaction has a tiny rounding difference (£312.00 vs £311.98 after FX).

The **amount tolerance** and **date window** are configurable in `config/settings.py`.
Among all candidates in the window, we pick the one whose description is most similar to
the bank line. Confidence is computed as: `avg(amount_confidence, date_confidence, description_similarity)`.

Any match below 0.70 confidence is flagged for human review.

---

#### Level 3 — Description Fuzzy Match (the interesting one)

This is where the **vendor matching pipeline** runs. It is itself a 4-tier cascade:

**Tier 1 — Normalization** (`engine/vendor_matching/normalizer.py`)

Before any comparison, both the bank description and the invoice vendor name are run
through a canonicalization pipeline. This is where most of the magic happens.

Example: `PYPL * INGRAM CONTENT GRP NASHVILLE #TXN87234 04/15 CA`

The normalizer strips, in order:
1. **Brand identity substitutions** — `AMZN` → `AMAZON`, `MSFT` → `MICROSOFT`, etc.
2. **Pure processor prefixes** — `SQ *`, `PYPL *`, `STRIPE *`, `TST *` (payment intermediaries;
   the vendor is what follows the asterisk)
3. **Bank noise prefixes** — `POS PURCHASE`, `DEBIT CARD`, `ACH DEBIT`, `WIRE TRANSFER`,
   `UPI`, `NEFT`, `RTGS`, etc.
4. **Trailing transaction IDs** — anything matching `[A-Z0-9]*\d{4,}` (must contain a digit
   to avoid stripping pure-alphabetic vendor names like "DAILYBEAN")
5. **Embedded dates** — `04/15`, `15APR`, etc.
6. **Location tails** — US state codes, country suffixes, city names at end of string
7. **Corporate suffixes** — `INC`, `LLC`, `LTD`, `PVT LTD`, `CORP`, `GmbH`, `PLC`, etc.

Result: `PYPL * INGRAM CONTENT GRP NASHVILLE #TXN87234 04/15 CA` → `INGRAM CONTENT GRP`

The invoice vendor `Ingram Content Group Ltd` → `INGRAM CONTENT GROUP`

Now you have two clean strings that can be compared.

**Tier 4 — Alias Lookup (O(1), runs before lexical scoring)**

If the user has previously approved a match and saved a vendor alias (e.g., "INGRAM CONTENT GRP"
→ "Ingram Content Group"), that lookup happens first. It's O(1) — just a dictionary read.
Matching is intentionally generous: exact match, then canonical match, then substring match
(with a ≥4-character minimum to avoid overly broad triggers). The longest matching alias wins.

If an alias hit occurs and the alias matches an invoice vendor exactly: score = 1.0,
method = "alias-exact". This is the self-learning feature — every approved match can teach
the system a new rule, silently, forever.

**Tier 2 — Composite Lexical Similarity**

Four metrics, each addressing a different failure mode of the others:

| Metric | Weight | What it solves | Example |
|--------|--------|----------------|---------|
| Jaro-Winkler | 35% | Prefix-heavy; vendors usually share starts | `STRIPE` vs `Stripe Inc` |
| Token Set Ratio | 25% | Word-reorder tolerant | `Amazon Inc` vs `Inc Amazon` |
| Token Sort Ratio | 15% | Order-sensitive discriminator | Distinguishes similar names |
| Partial Ratio | 25% | Substring-friendly | `AMZN` vs `Amazon Marketplace` |

**Composite score** = weighted average across all four.

**Threshold logic:**
- Composite ≥ 0.95 → "locked in" — skip embedding (save compute on obvious hits)
- Composite < 0.95 → proceed to Tier 3

**Tier 3 — Embedding Cosine Similarity**

Uses `fastembed` with the **BGE-small-en-v1.5** model (384 dimensions, runs entirely
locally — no API call, no internet required). The model is loaded once at startup (~5-10s)
and is LRU-cached per string, so repeated lookups are free.

Why embeddings at all, if the lexical scorer is already good?

Because abbreviations and semantic variants defeat lexical matching entirely:
- `DAILYBEAN` vs `The Daily Bean Coffee` → lexical: ~0.30 (fails). Embedding: 0.87 (succeeds).
- `BK ROASTERS` vs `Brooklyn Book Roasters` → partial overlap on `BK`; embedding picks up
  the full semantic match.

The embedding score is only trusted above 0.60 (the `EMBEDDING_FLOOR`). If it's below that,
it's treated as no signal. If it passes, we compute a blended score:

```
blended = 0.65 * embedding_cosine + 0.35 * composite_lexical
final   = max(composite_lexical, embedding_cosine, blended)
```

"Ensemble max" — any strong signal can rescue a marginal one. A 0.95 lexical + 0.50
embedding doesn't get dragged down; the lexical score wins outright.

**Amount gate:** after the vendor score, the amount must agree within 10% relative tolerance.
The first candidate that passes both the vendor score threshold AND the amount gate wins.

**Score cap for non-deterministic methods:** alias-exact and canonical-exact can score
up to 1.0 (eligible for auto-approve). Fuzzy/embedding matches are capped at 0.85 and
always flagged for human review — deliberately, because they are probabilistic.

---

#### Level 4 — One-to-Many Match (subset sum)

**The problem:** a single bank deposit of £850 corresponds to three separate invoices of
£300, £400, £150 that were paid together.

**The solution:** PuLP (Python integer programming library) runs a **subset-sum solver**.
For each unmatched bank line, it looks at all unmatched ledger entries within a 7-day date
window and asks: "is there a subset whose sum equals this bank amount within tolerance?"

This is a classic NP-hard problem, but PuLP's branch-and-bound solver handles the typical
range (10–50 candidates) in milliseconds. All results are flagged for human review (score
around 0.80).

---

#### Level 5 — Many-to-One Match (installment payments)

The inverse of Level 4: **multiple bank lines sum to one invoice** (e.g., a client paying
a large invoice in three instalments).

Algorithm:
1. Gather remaining unmatched bank lines and unmatched invoices.
2. For each invoice, identify candidate bank lines by date window + vendor similarity
   (using the same vendor matcher at a relaxed threshold of 0.45).
3. Run subset-sum on that candidate block: do any N bank lines (N ≥ 2) sum to the
   invoice amount?
4. If yes, update all N `MatchResult` records to status `many_to_one`.

---

#### Level 6a — Relaxed Deterministic Match

A second-chance pass with loosened thresholds (vendor threshold 0.45, date window 14 days,
amount tolerance 5% relative). Always emits status `possible` — the lowest confidence tier.
Score hard-capped at 0.65.

---

#### Level 6b — LLM Verifier (last resort)

Whatever remains after all 6 deterministic levels gets sent in a **single batched LLM call**
to the language model (via OpenRouter / Gemini fallback). The LLM receives all remaining
unmatched pairs and is asked to find matches.

Design constraints:
- Only runs if both the unmatched bank set AND the unmatched invoice set have ≤ 30 entries
  (otherwise the call would be slow and the LLM would get confused by the combinatorics).
- All results are capped at `possible` status, score ≤ 0.65, always require human approval.
- Structured output via Pydantic — LLM must return a JSON schema, not free text. Invalid
  schemas are discarded silently.
- The prompt is conservative by design: `"false positives are worse than misses, return null
  when in doubt."`
- LLM failure never crashes the cascade — the try/except is intentional, not lazy.

---

### 2.3 The self-learning alias system

Every time a human approves a match in the Reconcile screen, they see a checkbox: **"Remember
this vendor for future imports"**. If they tick it, the system records:

`"SQ * DAILYBEAN COFFEE" → "The Daily Bean Coffee"`

From that point forward, whenever that pattern appears in any future import, it scores 1.0
immediately (alias-exact match) and skips all 4 scoring tiers. The system builds a
permanent, auditable dictionary of vendor mappings, specific to each organisation.

The alias lookup is also intentionally fuzzy: it does substring matching with a minimum
4-character key length, so `"INGRAM CONTENT GRP"` as an alias will catch
`"PYPL * INGRAM CONTENT GRP NASHVILLE #TXN..."` — you don't need an exact match.

---

### 2.4 Vendor timing memory

The system passively learns each vendor's typical payment behaviour. If "Acme Ltd" always
pays 3–5 days late, the engine adjusts its expected date window for that vendor specifically,
rather than marking every Acme payment as "late" indefinitely. This stops habitual late
payers from being permanently flagged, and keeps the "true anomalies" signal clean.

---

### 2.5 Multi-tenancy (every org is isolated)

Every table in the database has an `org_id` column. Every API endpoint is authenticated and
scoped: `_load_X_for_org()` throws a 404 if you try to access another org's data. The
session cookie is httpOnly. Passwords are bcrypt with cost factor 12.

You can demo multiple organisations in the same running app — they share nothing.

---

### 2.6 The knowledge base and assistant

Each organisation has its own vector knowledge base, built on **Qdrant** (a local vector
database). When documents are uploaded (invoices, policy docs, SOPs), they are:
1. Chunked into ~512-token segments
2. Embedded with BGE-small-en (dense) and BM25 (sparse)
3. Stored in Qdrant with org-scoped filtering

The **chat assistant** (Groq llama-3.3-70b) can then answer questions like:
- *"How much does Acme Ltd still owe us?"* (queries the SQL database via a structured tool)
- *"What is our policy on late payments?"* (retrieves from the org's KB via hybrid RRF search)

RRF = Reciprocal Rank Fusion: combines the dense embedding ranking and the BM25 keyword
ranking into one merged ranking that is consistently better than either alone.

## Part 3 — What others do (the competitive landscape)

### 3.1 Xero

Xero is the gold standard reference for the UI and the UX of reconciliation. Their approach:
- **Rule-based matching**: user defines rules ("whenever description contains SPOTIFY, match
  to account X"). Rules require manual setup and maintenance.
- **"Suggested match"**: uses exact amount + approximate date, with some simple string
  matching. The match suggestions are good but not semantic.
- **No learning**: each mismatch must be manually handled or a new rule written.
- **No explainability**: Xero shows you a match, it does not tell you *why* it matched.
- **Overpayments/Credits**: Xero-style credit notes — this is implemented here too.

**Our advantage vs Xero:** semantic vendor matching (embeddings), self-learning aliases,
full reasoning chain on every match, and the chat assistant.

### 3.2 QuickBooks

Very similar to Xero. Rule-based, amount+date focused, some machine learning claimed in
their marketing but the underlying matching is not fundamentally different.

**Key gap in both:** neither handles the "noisy description" problem systematically. They
rely on you teaching them the rules manually. We do it automatically.

### 3.3 Sage / older systems

Purely rule-based. No fuzzy matching. Best for businesses with very clean, consistent bank
data. Breaks the moment the data is messy, which is most of the time.

### 3.4 What the research says

The academic literature on bank reconciliation and invoice matching converges on a few findings:

1. **Lexical similarity alone (edit distance, n-gram) is insufficient** for real-world bank data
   because the same merchant can appear under 20+ different strings depending on the payment
   channel. The 2019 PwC benchmarking study found >35% of reconciliation mismatches were due
   to vendor name inconsistency, not genuine discrepancies.

2. **Ensemble approaches outperform single-metric approaches.** Combining Jaro-Winkler (good
   for prefixes), token set ratio (good for reordering), and partial ratio (good for
   abbreviations) gives ~15–20% better recall than any single metric. This is what the
   composite scorer in Tier 2 implements.

3. **Dense embeddings (BERT-family) rescue the semantic matches that lexical methods miss.**
   Studies on entity matching consistently show that transformer-based embeddings catch
   ~10–15% additional true matches that all lexical methods miss. The BGE-small model (used
   here) is specifically trained for passage retrieval and entity matching tasks, not general
   language — it is one of the best-performing models at its size class.

4. **Human-in-the-loop is not just a feature, it's a risk management requirement.** The
   Basel III framework and IFRS 9 accounting standards both require human review of automated
   matching for anything above a de-minimis threshold. A fully automated system would be
   non-compliant in most regulated environments. The architecture here — auto-approve only at
   Level 1 (exact match, confidence 1.0), human review for everything else — maps directly
   onto this requirement.

5. **One-to-many and many-to-one matching (split/installment payments) is the hardest
   unsolved problem in the space.** Subset-sum is NP-hard in theory, but practical instances
   in reconciliation are small enough (10–50 candidates) that integer programming solvers
   (PuLP/CBC) solve them in milliseconds. This is genuinely novel compared to what
   commercial tools offer — none of Xero, QuickBooks, or Sage handle installment payments
   programmatically.

## Part 4 — The thought process behind the build

### 4.1 Where it started

The starting intuition was simple: *reconciliation is a search problem.* You have a query
(the bank line) and a corpus (the invoices/bills), and you need to find the best match.
This is structurally identical to search — and search has been solved very well by embedding
models and vector similarity.

The first version of the engine was purely embedding-based. Every bank description and every
invoice vendor was embedded, and cosine similarity was used to rank candidates. It worked
surprisingly well on clean data.

The problem: **embeddings are opaque and non-deterministic.** You can't explain to an
auditor why the system matched `SQ * DAILY BEAN` to `The Daily Bean Coffee` in a way they
can verify. And running embeddings on every pair is slow.

### 4.2 The insight: determinism first, embeddings as rescue

The shift in thinking: **most matches are not semantically ambiguous.** If the amount is
exactly right and the date is exactly right, there is no need for machine learning. The
embedding should only be invoked when the evidence is genuinely ambiguous — in the zone
where human judgment is also uncertain.

This led to the cascade design:
- **Levels 1-4:** pure deterministic, no ML, full auditability, very fast.
- **Tiers 2-3 within Level 3:** embedding as a fallback for the ambiguity zone only.
- **Level 6b:** LLM as absolute last resort, always under human review.

The result is a system that is **mostly deterministic** (and therefore auditable and fast)
but **gracefully degrades** to probabilistic methods when the data genuinely requires it.

### 4.3 The multi-agent architecture

The system is also designed as an **MCP server** (Model Context Protocol — Anthropic's
open standard for connecting LLMs to tools). The matching engine is wrapped in MCP tools:
`reconcile`, `get_unmatched`, `approve_match`, `store_vendor_alias`, `search_kb`.

This means the system can be driven by:
1. A human via the React UI (today's demo)
2. A language model via the MCP server (any Claude-compatible client can reconcile autonomously)
3. A CLI agent (the `agent/engine.py` module — Anthropic SDK + tool registry)

The same engine, three interfaces. This is what "multi-agent" means in the project name.

### 4.4 The data model choices

- **SQLite** (not Postgres for now): the matching engine is CPU-bound, not DB-bound.
  For a single-tenant or low-concurrency deployment, SQLite is not a limitation — it's
  a simplification that eliminates infrastructure overhead for the demo and early customers.
  The `DATABASE_URL` env var is the only change needed to switch to Postgres when the
  time comes.
- **SQLModel** (not raw SQLAlchemy): Pydantic validation at the model layer, async-ready,
  less boilerplate. The schema is in `memory/models.py`.
- **Every table has `org_id`**: multi-tenancy was designed in from day 1, not retrofitted.
  This is important — retrofitting multi-tenancy is a very painful migration.

### 5.3 The dilemma: when to use LLM for matching

This is the live tension in the design. The conservative position (current) says: LLM only
for last-resort, always under human review, confidence hard-capped at 0.65.

The argument for more LLM: modern instruction-tuned models are remarkably good at reasoning
about business names and payment patterns, and could improve recall on the genuinely hard
cases — vendor names with no lexical overlap and no prior alias.

**The counter-argument (why the current design is right for now):**
1. LLM outputs are not reproducible — the same inputs can give different outputs between
   API versions, making regression testing impossible.
2. LLM matches in an accounting context require a clear audit trail. "The model said so" is
   not an acceptable answer to an auditor or a regulator.
3. LLM cost is unbounded if naively applied to every pair in every run.
4. The deterministic cascade already covers 80-90% of cases. The marginal gain from LLM
   on the remaining 10-20% is real but not large enough to justify the tradeoffs.

**The right move forward:** use LLM to *generate candidate rules*, not to *make decisions*.
If the LLM repeatedly sees a pattern (`PYPL * XYZ` → invoice from `XYZ Corp`), it could
propose a new normalizer rule or a new alias automatically — subject to human approval.
This keeps the decision-making deterministic while using LLM for rule discovery.

## Part 6 — Where this is going

### 6.1 Immediate (next sprint)

- Wire the "auto-reconcile all Level-1 matches" button in the UI.
- Fix the `org_id NOT NULL` migration.
- Server-side chat history.

### 6.2 Near-term

- **Statement-level rules**: allow users to define custom matching rules per account
  (e.g., "for this account, match within 5 days not 3"). Stored in the DB, visible in the UI.
- **Batch review mode**: approve/reject 20 matches at once from a summary view, not one-by-one.
- **Export to ledger**: generate journal entries in Xero/QuickBooks format from reconciled matches.

### 6.3 Architectural evolution

- **Postgres + read replicas** when concurrency becomes a concern. One config line change.
- **Real-time streaming**: replace the batch import with a live bank feed (Open Banking API).
  Each new transaction arrives and is matched instantly. The matching engine is already
  stateless and pure-function — it's designed for this.
- **Feedback loop into the normalizer**: when the LLM verifier repeatedly matches the same
  noisy pattern, propose it as a new normalizer rule. Close the loop between the probabilistic
  tail and the deterministic core.
- **Fine-tuned embedding model**: the BGE-small model is general-purpose. Fine-tuning it on
  a corpus of (bank description, vendor name) pairs would move the embedding accuracy from
  "good" to "very good" for the specific vocabulary of bank statements.

## Part 7 — The things to say when questions come in

**Q: "Why not just use ChatGPT to match everything?"**

Because accuracy without auditability is dangerous in accounting. When a match is wrong —
and some will always be wrong — you need to know exactly why it was made, who approved it,
and what the evidence was. The audit trail in this system stores the full `reasoning_path`
for every match, at every level. A language model cannot provide that. Beyond auditability:
cost, speed, determinism, and the fact that the deterministic engine already handles ~85%
of cases perfectly.

**Q: "How is this different from what Xero/QuickBooks already does?"**

Three things. First, **semantic vendor matching**: they match on rules and exact strings;
we match on normalized text similarity + embeddings, so we catch vendor names that would
break a rule-based system. Second, **self-learning**: every approved match can teach the
system a new alias — no manual rule-writing. Third, **split/installment payment matching**:
the subset-sum solver handles complex payment structures that no commercial tool handles
automatically.

**Q: "What's the match rate?"**

On the "my zoo" demo org with 511 statement lines, the overall match rate is visible in
the Dashboard. Typical real-world data shows 60-75% at Level 1 (exact), with Levels 2-4
bringing that to 85-90%, and Levels 5-6 + human review handling the rest.

**Q: "Is this ready to go to production?"**

The core matching engine — yes. The product gaps are in the UI workflow (batch review,
auto-reconcile button), not in the accuracy of the matching. For a small business or
accounting firm with clean data, it's ready to run. For a regulated financial institution,
the `org_id NOT NULL` migration and the server-side chat history would need to be done first.

**Q: "What does the multi-agent part actually mean?"**

The matching engine is exposed as an MCP (Model Context Protocol) server. Any Claude client
— Claude Desktop, Claude.ai, or a custom Claude agent — can call the matching engine as a
tool. So you can ask Claude: "reconcile the attached CSV" and it will call `reconcile()`,
then `get_unmatched()`, then `approve_match()` for the high-confidence ones, and then ask
you about the rest. The human UI and the AI interface both talk to the same engine.
